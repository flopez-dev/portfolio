# CLAUDE.md

## What this repo is

Francisco López's personal site, and inside it the landing pages he has built for
individual businesses — one self-contained folder per business under `projects/`, each
one still deployable on its own.

The root is an Astro site (Spanish at `/`, English under `/en/`). Every folder under
`projects/` is plain static HTML with no build step, published unchanged at its own flat
URL. Those two facts are held together by one integration; see "The landings" below.

## Structure

The root is a normal Astro project:

```
astro.config.mjs          site/base from env, i18n, sitemap, the landings integration
wrangler.jsonc.disabled   the site's own Worker, waiting for a domain
integrations/landings.mjs publishes projects/*/public/ without touching it
src/
  config.ts               contact details and profile links, in one place
  content.config.ts       typed schema for the project write-ups
  content/projects/{es,en}/*.md   one file per project and language, same slug
  components/ layouts/ pages/ styles/ lib/ i18n/
public/img/previews/      full-page screenshots, generated by tools/preview-shots.sh
```

Each landing keeps the skeleton it always had:

```
projects/<business>/
├── wrangler.jsonc
└── public/
    ├── index.html
    ├── css/styles.css
    ├── js/main.js
    └── assets/img/
```

`public/` is the static content actually served — everything in it is publicly accessible
at the landing's URL. `wrangler.jsonc` (the Cloudflare Workers config, see "Deployment"
below) stays a level above it deliberately, so it's never served. A landing without a
domain yet, or whose domain isn't live in Cloudflare yet, has no `wrangler.jsonc` — see
"Adding a new business" below. When a landing is paused rather than not-yet-configured
(its domain got deferred, its content isn't ready), rename its config to
`wrangler.jsonc.disabled` instead of deleting it — `deploy.yml`'s `find` only matches the
exact `wrangler.jsonc` name, so a `.disabled` file is invisible to it but the routes and
settings stay on hand for whenever it's reactivated (see `projects/magma_consulting/`,
paused this way pending a real domain).

Current landings: `projects/chantal_verdugo_house/` (live and indexed, deployed on
Cloudflare — the only landing with a domain of its own) and `projects/inmica/` (finished
client work with no live domain; indexed as part of this site rather than `noindex`,
since it has nowhere else to be canonical — see "Deployment" below).
`projects/latiguillos_laguia/` and `projects/magma_consulting/` are scaffolds: real
structure, placeholder content, `noindex`. See the table in `README.md` for status and
keep it in sync when a landing's status changes.

## The root site

The root is a bilingual personal site: web work for local businesses as the front door,
Product Owner / Delivery Lead as the second thread. Routes, duplicated by hand rather
than through a routing layer, because there are only five of them:

| Spanish | English |
| --- | --- |
| `/` | `/en/` |
| `/proyectos` | `/en/projects` |
| `/proyectos/[slug]` | `/en/projects/[slug]` |
| `/servicios` | `/en/services` |
| `/perfil` | `/en/profile` |

There is no contact page: `src/components/Contacto.astro` closes every page instead.

- **Spanish first, with an English half.** Interface strings live in `src/i18n/es.json`
  and `en.json` behind a `t(lang)` helper; page prose lives in the page files themselves,
  which is the point of duplicating them. Every page passes both of its own paths to the
  layout, so the language switch lands on the equivalent page and `hreflang` is exact.
- **Project write-ups are content, not pages.** `src/content/projects/es|en/<slug>.md`,
  one file per language sharing a slug, validated by `src/content.config.ts`. Two fields
  beyond the obvious: `landing` (the folder under `projects/` whose site is published
  here — the public URL is derived from it, never written by hand) and `estado`, because
  two of the four projects are scaffolds and showing them as finished work would be a lie.
- **Preview screenshots.** Real full-page captures at `public/img/previews/<folder>.{webp,jpg}`,
  generated by `tools/preview-shots.sh` — not hand-maintained. Re-run it after any visible
  change to a landing. They are served as plain `<picture>` rather than through
  `astro:assets`: they are already hand-tuned webp+jpg pairs, and re-encoding lossy output
  gains nothing. `src/lib/imagen.ts` reads their real dimensions at build time so the
  `width`/`height` attributes stay honest when a capture is regenerated.

## The landings

`integrations/landings.mjs` is the whole story of how `projects/` reaches the browser
without being modified:

- In `npm run dev` it mounts each `projects/<folder>/public/` with `sirv`, so the landings
  answer at their real URLs while you work.
- In a build it copies each one to `dist/<slug>/` — flat, not under `dist/projects/`, and
  without the `wrangler.jsonc`. Both deploy targets publish `dist/`, so one copy serves
  both.
- The slug map lives in `src/lib/landings.mjs` (`chantal_verdugo_house` → `chantal-house`,
  `magma_consulting` → `magma-consulting`); everything else uses its folder name. It used
  to be a bash array inside the deploy workflow.
- `noindex` on a duplicate copy is **derived, not listed**: if a landing's own
  `<link rel="canonical">` doesn't match the URL it is being published at, that copy is a
  duplicate and gets `noindex, nofollow` — in the build output only. That is why the
  GitHub Pages copy of `chantal_verdugo_house` is `noindex` (it is canonical on its own
  domain) while `inmica` stays indexable there (Pages *is* its canonical home), with no
  per-landing list to maintain.

`diff -r dist/<slug> projects/<folder>/public` is the check: it must come back clean for
every landing except `chantal-house`, which differs by exactly the robots meta line.

## Constraints

- **No build step inside `projects/`.** No framework, no bundler, no `package.json` of
  their own — plain HTML, CSS and JS, exactly as before. The *root* does build (Astro +
  Tailwind); that boundary is the point, and the landings never learn about it.
- **No CDN or external dependencies.** A landing must render correctly opened straight
  from disk (`file://`) and on plain static hosting. Fonts, icons and scripts are vendored
  into the landing's own `assets/`. The root site follows the same rule through its build:
  fonts come from Fontsource and are bundled, never fetched from Google Fonts.
- **Vendored media needs a license that actually allows it.** Content pulled from a
  client's existing site (their own text, photos) is fine to reuse — it's theirs. Stock
  assets are a different question: a client's paid stock subscription doesn't transfer to
  a site hosted somewhere else, so any stock photo/video/icon sourced independently needs
  a license that explicitly permits commercial redistribution (Pexels/Pixabay/Mixkit-style
  "free for commercial use," not assumed from context). See the comment above
  `projects/magma_consulting/assets/img/hero-bg.mp4` in its `index.html` for how that's
  documented inline — record the source and license terms next to the asset, not just in
  a commit message.
- **Assets stay scoped.** A landing never references files from another landing, or from
  the root site. If two landings need the same thing, duplicate it — there is no `shared/`.
- **Relative paths only, inside a landing.** No leading `/` in `href`/`src`, so a folder
  works from any subpath on a host. In the root site the equivalent rule is `withBase()`
  from `src/lib/paths.ts`: Astro rewrites `base` into bundled assets but not into a
  hand-written `<a href>`, and GitHub Pages serves the site from `/portfolio/`. The build
  fails on a root-relative link that skips the base, so this can't ship broken.
- **Astro is pinned exactly** (`"astro": "7.2.10"`, no caret). 7.3.0 injects an import of
  `astro/_internal/logger`, which that package doesn't export, and the build dies. Re-test
  before moving the pin.

## Conventions

For a landing under `projects/`:

- Folder names: lowercase, underscores instead of spaces (`my_business`).
- One `index.html` per landing. Extra pages sit alongside it as a flat file
  (`privacy.html`) by default; use a subfolder with its own `index.html`
  (`privacy/index.html`) instead if the page needs a clean, extension-less URL — see
  `projects/magma_consulting/` (its `aviso-legal/`, `privacidad/`, `cookies/`), used
  there because `canonical`/`sitemap.xml` already declared trailing-slash URLs for them.
- Keep `index.html` semantic: `<header>`, `<main>` with sections, `<footer>`.
- Every page carries `<title>`, `<meta name="description">` and Open Graph tags filled in
  for that specific business.
- CSS uses custom properties declared on `:root` for the palette and type scale.
- `main.js` is loaded with `defer`.

For the root site:

- Palette and type scale are Tailwind theme tokens in `src/styles/global.css`, named
  after the thing they come from (`cal`, `rotulo`, `azulejo`, `ocre`, `piedra`), not
  after their role.
- No client JavaScript. The header works without it; there is no menu toggle to break.
- Internal links go through `withBase()`. Landing URLs go through `slugFor()`.
- Contact details and profile links live only in `src/config.ts`. Placeholders there
  fail loudly and print a warning during the build.

## Local preview

From the repo root, for the site and every landing together (the landings are served
from `projects/` live, no copy):

```sh
npm install
npm run dev
```

The site is at `http://localhost:4321/portfolio/` — the base path matches GitHub Pages, so
dev and production agree. A landing on its own still works with no tooling at all:

```sh
cd projects/<business>/public && python3 -m http.server 8000
```

## Deployment

Two independent deploys run off this repo, and each channel has exactly one triggering
branch so the two never race over the same published output: `develop` → GitHub Pages,
`main` → Cloudflare.

`astro.config.mjs` reads `SITE_URL` and `BASE_PATH` from the environment, defaulting to
GitHub Pages (`https://flopez-dev.github.io` + `/portfolio/`) because that is where the
site actually lives today. A build for a domain of its own sets `BASE_PATH=/`.

### The site — GitHub Pages

`.github/workflows/deploy-pages.yml` runs on push to `develop` (and via manual
`workflow_dispatch`): `npm ci`, `npm run build` with the Pages base path, and publishes
`dist/`. The build itself copies every landing in flat (see "The landings" above), so
adding a business needs no workflow change — only a shorter public slug does, and that
goes in `src/lib/landings.mjs`, not in the workflow.

### The site — Cloudflare Workers

`wrangler.jsonc.disabled` and `.github/workflows/deploy-site.yml.disabled` are written
and waiting for a real domain. Turning them on: fill in the routes, drop the `.disabled`
from both filenames, set `SITE_URL` in the workflow, and add a `CLOUDFLARE_API_TOKEN`
repo secret scoped to that Worker. Once the site is canonical on its own domain, the
Pages copy should get a `noindex` — and note that Pages cannot simply be retired, because
`projects/inmica/public/index.html` hardcodes its Pages URL as its canonical and that file
is not ours to edit.

### Landings — Cloudflare Workers

Each landing with a `wrangler.jsonc` deploys as its own Worker with Static Assets, serving
its `public/` directory — see the file for the `name`, `assets.directory` and `routes`.
Only landings with a real, live domain keep an active `wrangler.jsonc`; see the note on
`.disabled` configs above.

`.github/workflows/deploy.yml` runs on push to `main`. It finds every `wrangler.jsonc`
**under `projects/`** — deliberately scoped, so the root config never lands in the matrix —
then runs `npx wrangler deploy` from each of those directories in a matrix job. A landing
without a `wrangler.jsonc` is never deployed. No build step here either.

Each landing authenticates with its own token, kept as a repo secret named
`CLOUDFLARE_API_TOKEN_<FOLDER-UPPERCASED>` (e.g. `chantal_verdugo_house` →
`CLOUDFLARE_API_TOKEN_CHANTAL_VERDUGO_HOUSE`) — the workflow derives that name from
`matrix.proyecto` and looks it up dynamically, so one landing's token never has to be
scoped wider than the Worker it deploys. `CLOUDFLARE_ACCOUNT_ID` is the one secret shared
by every landing, since they all deploy into the same Cloudflare account.

## Adding a new business

1. Copy an existing folder under `projects/` and rename it after the business.
2. Reset the content of `public/index.html`, `public/css/styles.css` and
   `public/js/main.js`.
3. Update `<title>`, the meta description and the Open Graph tags.
4. Drop `favicon.ico` and `og.jpg` into `public/assets/img/` — `index.html` already
   points at both, and they 404 until the real files are added.
5. While the landing is still a scaffold, add
   `<meta name="robots" content="noindex, nofollow" />` — the site will link it publicly
   before the content is real. Remove it once the content is real.
6. Add the business to the table in `README.md`, linking to `projects/<name>/`.
7. Run `tools/preview-shots.sh <folder-name>` (bare name, e.g. `inmica` — the script
   resolves it under `projects/`) to generate its preview.
8. Write the write-up: `src/content/projects/es/<slug>.md` and `en/<slug>.md`, same slug,
   with `landing: '<folder-name>'` so the live link is derived. It shows up on
   `/proyectos` automatically; set `destacado: true` to put it on the home page.
9. If the folder name would make an awkward public URL, add a shorter slug for it to
   `SLUG_OVERRIDES` in `src/lib/landings.mjs`. Most landings don't need this.
10. Once the business has a domain, add `projects/<name>/wrangler.jsonc` (copy an
    existing one and update `name`, `routes` and the domain), and add a
    `CLOUDFLARE_API_TOKEN_<NAME-UPPERCASED>` repo secret holding a token scoped to just
    that Worker, so `.github/workflows/deploy.yml` picks it up on the next push to `main`.
11. Sanity pass: keyboard-only navigation, and nothing moves under
    `prefers-reduced-motion: reduce`.
